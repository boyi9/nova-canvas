# P3 规划：从"能力就绪"到"生产可用"

> **文档版本**：v1.0
> **前置**：P0（稳定性/安全）、P1（修图/生成）、P2（协作/音频/游戏资产）已完成并提交
> **基线**：后端 649 用例通过；前端 `tsc` 0 错误、`vitest` 158 通过、`vite build` 9081 模块绿；后端路由 98 条
> **状态**：待启动

---

## 1. 背景：P2 交付了什么，缺什么

P2 完成了**能力层**——三套可用的规格计算与编排引擎（协作、音频、游戏资产），接口契约稳定、测试完备、文档与实现双向锁定。

但三者都停在"最后一公里"之前：

| 模块 | 已完成 | 缺口 | 缺口性质 |
|---|---|---|---|
| 协作 | RBAC/分享/版本/审批/排期/Presence 25 接口 | 多人实时光标与文本协同 | 传输层 |
| 音频 | 目录/规划/混音/渲染 13 接口 | `render` 产出正弦波而非人声 | 外部服务 |
| 游戏资产 | 规格计算 5 接口 | 只算参数，不产像素 | 外部服务 |

**共同特征**：缺口都在"替换一个实现"而不在"重写一套接口"。
P2 刻意把接口与实现解耦（规划/渲染两阶段、`PresenceBus` 事件抽象），正是为了让 P3 只换实现层。

---

## 2. P3 目标

1. **音频**：接入真实 TTS/BGM/SFX 合成，`render` 产出可交付音频
2. **协同**：presence 从轮询升级为 WebSocket 推送；画布内容支持并发编辑不互相覆盖
3. **游戏资产**：从规格计算延伸到实际图像产出
4. **交付**：补齐多格式导出，让"画布 → 可交付文件"闭环

---

## 3. 工作项与优先级

优先级判定依据：**用户可感知度 × 阻塞后续工作的程度**。

### P3-1 音频真实合成（P0，最高优先）

**为什么最优先**：这是三个缺口里唯一"接口已完备、只差实现"且用户立刻能感知价值的。一个只会"嘟——"的音频模块在产品上是不可展示的。

**设计**：
```
web/backend/audio/
├── catalog.py        # 已有：音色/BGM/SFX 目录
├── specs.py          # 规划（参数校验/时长/预算）
├── engine.py         # 已有：_plan_* + render_job  ← 只改这里
├── synthesizer.py    # 已有：本地正弦波（保留为降级方案）
└── providers/        # 新增：外部合成服务适配
    ├── __init__.py
    ├── base.py       # TtsProvider 协议：synthesize(text, voice) -> bytes
    └── openai_tts.py # 首个实现
```

**关键决策**：

| 决策点 | 方案 | 理由 |
|---|---|---|
| 接入方式 | Provider 协议 + 注册表 | 已有多模型供应商注册表的先例（`models/providers/registry.py`），复用模式 |
| 凭据 | 环境变量，绝不入库 | 安全基线要求；`.env.example` 已存在 |
| 失败降级 | 无凭据时回退本地 sine | 保证开发/CI 环境可用，测试不依赖网络 |
| 异步性 | 复用既有 async job | 真实 TTS 耗时秒级，同步会阻塞请求 |
| 幂等 | 保留 `render` 幂等 | 外部调用有费用，重试需可控 |

**验收标准**：
- [ ] `POST /jobs/{id}/render` 在有凭据时返回真实人声 WAV（`wav_info().duration_s` 与预估偏差 < 15%）
- [ ] 无凭据时自动降级并返回 `output.degraded: true`（而非报错）
- [ ] `tests/test_audio.py` 新增 provider 层用例（mock provider，不依赖网络）
- [ ] 文档 §2.2"合成模式说明"更新为真实说明
- [ ] 成本与错误在 `AudioJob` 留痕（外部调用失败不得静默）

**风险**：真实 TTS 时长与预估模型（4.5 字/秒）可能偏差大。需在接入后重新校准 `_speech_duration`，并考虑按 provider 分别校准。

### P3-2 实时协同传输层（P1）

**设计**：`PresenceBus` 已抽象 `join/leave/cursor/typing` 并发射事件，替换传输层即可：

```
web/backend/collab/
├── presence.py       # 已有：PresenceBus（业务逻辑，不动）
└── ws.py             # 新增：WebSocket 端点
```

```
ws://localhost:8000/ws/collab/{project_id}?token=<jwt>
   ├── client → server: { "t": "cursor", "x":..,"y":..,"zoom":.. }
   ├── client → server: { "t": "typing", "typing": true }
   └── server → client: { "t": "presence", "online":[...] }   # 广播
```

**关键**：
- 鉴权复用 `verify_token`，禁止 URL 之外的注入
- 连接断开必须清理 session（否则幽灵在线）
- **保留 REST 端点**：移动端/弱网轮询仍是有效降级路径；文档已说明
- 加一条"并发编辑"策略：presence 只解决"看到别人"，不解决"不覆盖别人"。后者需要 CRDT（yjs）或字段级锁——**这是独立工作项，见 P3-4**

**验收标准**：
- [ ] 两个客户端连同一项目，A 移动光标，B 在 200ms 内收到（含心跳）
- [ ] 断开连接后 `presence` 列表在 1s 内移除该用户
- [ ] 非法 token 拒绝连接（WS close code 1008）
- [ ] 心跳断线重连后 session 复用（不重复计入 online）
- [ ] REST 端点保留，原有用例继续通过

### P3-3 游戏资产从规格到像素（P1）

**设计**：`specs.py` 的输出（帧尺寸、出血、色板）已是生成器所需的完整参数集，直接作为图像生成任务的 input_spec：

```
plan_texture()  →  spec  →  图像生成任务（异步 job）  →  图片 + 打包元数据
```

**关键决策**：
- **不自己做打包器**：产出 PNG 帧 + 一份 JSON 打包清单，交给引擎/既有工具链（TexturePacker 等）
- 复用既有 `services/async_job.py` 范式（提交→轮询→取回），与视频生成一致
- 规格校验前置：**非法规格不得进入生成**（否则浪费算力）

**验收标准**：
- [ ] `POST /game-assets/render` 接受 spec，返回 job_id
- [ ] 轮询可拿到生成结果 URL + 打包清单 JSON
- [ ] 非法 spec（出血过大等）在提交阶段即 `400`，不进入队列
- [ ] `tests/test_game_assets.py` 覆盖规格→任务的桥接

### P3-4 并发编辑防覆盖（P1，需专项方案）

**问题**：presence 只让人"看见"彼此，不阻止互相覆盖。editor A 和 B 同时拖动同一节点，后提交的会静默覆盖前者的结果。

**候选方案**：

| 方案 | 复杂度 | 权衡 |
|---|---|---|
| 字段级锁 | 低 | 实现快，但阻塞感明显，适合节点级粗粒度 |
| 操作日志 + 重放 | 中 | 需定义操作集，冲突检测复杂 |
| **CRDT（yjs）** | 高 | 无冲突，生态成熟，但引入依赖 + 需服务端部署 y-websocket |

**建议**：先做**字段级锁**（一个节点同一时刻只有一个 editor 可编辑，其他人只读）作为 P3 上线版；CRDT 留到 P4，需单独立项评估依赖成本。

**验收标准**：
- [ ] 节点被锁定时其他 editor 的编辑操作被拒绝并提示
- [ ] 锁持有者断开后锁自动释放（防死锁）
- [ ] 锁操作有审计日志

**验收标准**：

## 4. 建议执行顺序

```
P3-1 音频真实合成 ──┐
                    ├──→ P3-5 带音轨导出（依赖真实音频）
P3-2 协同传输层 ────┤
                    └──→ P3-4 并发编辑（依赖 WS）
P3-3 游戏资产 ──────┘（独立，可与以上并行）
```

**节奏建议**：P3-1 与 P3-2 并行（互不依赖），两者各自完成后 P3-5/P3-4 启动。P3-3 独立排期。

## 5. 质量门槛（沿用 P0-P2 基线）

任何 P3 工作项合并前必须满足：

- [ ] `pytest tests/ -q` 全绿，且新增功能有用例覆盖
- [ ] `npm run typecheck` 零错误

- [ ] `npx vitest run` 全绿

- [ ] 外部服务凭据只走环境变量，不得入库
- [ ] 外部调用失败不得静默，必须在返回体/日志中可见

## 6. 未纳入 P3（明确不做）

| 项 | 原因 |
|---|---|
| CRDT 协同 | 依赖成本高，需独立立项；先用字段级锁过渡 |
| 分布式部署 | 当前单实例够用；SQLite 到 Postgres 的迁移需专项 |
| 移动端原生 App | Web 已适配响应式，原生投入产出比不清晰 |
| 商业化（支付/会员深度） | billing 已有桩，深度流程需产品侧定案 |
